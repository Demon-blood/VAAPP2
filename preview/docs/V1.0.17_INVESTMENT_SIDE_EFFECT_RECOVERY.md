# v1.0.17 — Investment Side-Effect Recovery & Human Boundary Integrity

v1.0.17 hardens the two irreversible side-effect boundaries in Kraken investment autopilot: the outbound bank funding payment and the Kraken market order.

## Funding payment uncertainty

A network timeout or a provider response without a payment identifier is not a user decision. The original `InvestmentFundingTransfer` remains `creation_uncertain`, `requires_user_action` is false, any unbound authorization URL is suppressed, and historical `kraken_funding_uncertain` tasks are closed. VAAPP never creates a replacement bank payment for that intent.

Recovery queries transactions from the exact source bank account and accepts evidence only when exactly one booked debit matches amount, currency, Kraken creditor IBAN, the configured Kraken reference when present, and a narrow booking-date window. A transaction can bind to only one investment funding intent. Once recovered, the same transfer advances to `awaiting_deposit` and normal Kraken deposit reconciliation resumes.

## Trade uncertainty

Before an automatic Kraken order can cross the provider boundary, VAAPP persists an additive `InvestmentTradeIntent` with a stable Kraken `cl_ord_id`. Automatic trading now requires both query-open and query-closed order permissions in addition to modify-trades so an ambiguous order can be verified without replay.

Kraken `OpenOrders` and `ClosedOrders` are queried read-only by the original client order identifier. Exactly one provider order binds the intent and completes the original trade. Zero or multiple candidates remain VA-owned under reconciliation. Network loss, Kraken 429/5xx responses at AddOrder, or a successful response without a transaction id never authorize a second AddOrder.

Historical `trade_pending` rows without a v1.0.17 intent are assigned the legacy client-order identifier used by the original call and are reconciled only; they are never replayed.

## Human boundary

Only a bank authorization URL that is bound to a real external payment identifier may create the existing Kraken funding authorization task. Provider/system ambiguity never creates fake Needs You work.
