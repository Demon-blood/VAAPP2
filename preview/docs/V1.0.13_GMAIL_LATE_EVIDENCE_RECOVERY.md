# v1.0.13 — Gmail Late-Evidence Recovery & Delivery Continuity

v1.0.13 keeps ambiguous Gmail delivery under VA ownership for as long as provider evidence remains unresolved. It does not create a second Gmail provider submission.

## Failure mode closed

Before v1.0.13, an outbound Gmail POST that timed out or otherwise had an ambiguous provider outcome was correctly protected from automatic resend. VAAPP searched Gmail Sent using the deterministic RFC Message-ID for thirty minutes. If the message was still not visible after that window, however, the outbound row became `failed_uncertain`. The autonomous-core verifier then marked the objective step failed and the objective `blocked_system`, so later Gmail evidence was no longer reconciled automatically.

That made the system duplicate-safe but not continuously owning: a message that Gmail exposed in Sent after the arbitrary thirty-minute cutoff could remain permanently unresolved.

## v1.0.13 behavior

- `creation_uncertain` and `sent_unverified` remain reconciliation-only states; the provider submission is never repeated.
- The deterministic RFC Message-ID remains the external idempotency and provider-evidence key.
- Fast reconciliation is retained for fresh ambiguity, then provider queries back off to bounded slower intervals: two minutes, fifteen minutes, one hour, then six hours for long-lived uncertainty.
- There is no time-based transition from ambiguous delivery to terminal failure.
- Provider verification outages preserve the same VA-owned uncertainty state and use the age-sensitive backoff.
- Historical `failed_uncertain` rows are treated as migration input. They are normalized back to `creation_uncertain` and checked against Gmail Sent without resending.
- Historical Gmail objective steps that were previously failed solely because of `failed_uncertain` are reopened as `verifying`, allowing late provider evidence to complete the original durable objective.
- A definitive Gmail request failure remains a real system failure.
- Genuine Gmail authentication/authorization failure remains the existing human boundary (`failed_user`).
- No database migration is required.

## Completion evidence

Gmail delivery still completes only when VAAPP independently observes the exact stable RFC Message-ID under Gmail's `SENT` label. A successful API call or elapsed time is not completion evidence.
