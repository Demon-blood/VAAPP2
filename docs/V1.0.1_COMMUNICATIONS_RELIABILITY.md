# Full-Time VA v1.0.1 — Communications Reliability

Baseline: production v1.0 commit `66c09040326ac553a1402cd06fa6771344195d45`, GitHub Actions run #41 successful.

Release identity: backend `1.0.1`, Android `1.0.1+43`.

## Problem fixed

The v1.0 Communications screen could report all visible Android roles as enabled while a phone-history sync produced no user-visible result. The Flutter layer discarded the native sync payload, and the native HTTP bridge collapsed transport/backend errors to a null result. Incoming SMS and supported messaging notifications also had only a one-shot backend POST path, so a transient network/backend failure could prevent the real inbound event from reaching the VA ledger.

## Reliability contract

1. An inbound SMS is persisted in an Android-Keystore-encrypted device outbox before network dispatch. Successful direct ingestion removes the queued copy; failed dispatch remains queued and is retried by WorkManager.
2. Supported notification messages that fail live ingestion are retained as record-only queued events. RemoteInput reply authority is never persisted or replayed after the originating notification action is gone.
3. Manual SMS/call history synchronization uploads bounded chunks and returns explicit counts for rows scanned, processed, duplicates, queued recovery and policy synchronization. Native HTTP/backend-link errors are surfaced to the UI.
4. SMS history/call-log catch-up is evidence import and uses deterministic local classification rather than one AI call per historical record. Live incoming messages retain the normal decision path.
5. Communications health includes RECEIVE_SMS, encrypted pending-event count and the last native backend error.
6. Google Messages and Samsung Messages notifications can be observed by the notification listener for RCS/message visibility. This release does not claim arbitrary access to complete WhatsApp/Signal/Telegram/Messenger/RCS historical chat databases.

## Completion rule

A local notification, SMS database row, HTTP dispatch, or queued event is not itself proof that an outbound action completed. Existing carrier/provider evidence and domain postconditions remain required for completion.
