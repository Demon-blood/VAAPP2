# v1.0.11 — Fulfillment Side-Effect Recovery & Duplicate Suppression

## Problem

A browser fulfillment recipe can successfully perform a non-replay-safe provider action and still fail its final postcondition check. Before v1.0.11, that final verification miss could become an ordinary browser `failed` state. Fulfillment treats a failed action as finished, so a later reconciliation cycle could create a new action and a new idempotency key. For returns, refunds, cancellations, purchases, travel bookings, and similar provider mutations, that creates an unacceptable duplicate-execution risk.

## v1.0.11 behavior

- `BrowserOperation.side_effect_step` remains a durable ambiguity marker after a non-replay-safe side effect succeeds. It is cleared only after the explicit provider postcondition is verified.
- A final postcondition miss after such a side effect becomes `creation_uncertain`, not ordinary `failed`.
- The same browser operation can be resumed from `creation_uncertain`; its resume sequence changes, but the fulfillment action and business idempotency key do not.
- A resumed uncertain operation authenticates if necessary and performs provider-postcondition verification before any original recipe step can run.
- If the provider postcondition is still absent, the operation remains `creation_uncertain` and no mutating step is replayed.
- Browser security boundaries, provider timeouts, and runtime errors encountered during verification-only recovery also preserve `creation_uncertain`; they cannot downgrade an ambiguous mutation to ordinary `failed`.
- If the provider postcondition appears, the original operation becomes `verified` and Fulfillment completes from that evidence.
- Fulfillment keeps ambiguous provider outcomes VA-owned with `requires_user_action=false` and schedules another verification-only check.
- If safe verification-only recovery cannot be established, the request remains `blocked_system`, not `Needs You`.
- Genuine portal authentication challenges remain a separate human boundary through the existing `needs_user_auth` path.

## Safety invariant

A provider-side mutation is never repeated solely because its confirmation/postcondition was delayed, missing, or temporarily unverifiable.

## Release gates

The guarded GitHub Actions installer must pass the full backend test suite, Ruff, Flutter analysis/tests, Android release signing, and signed APK build before generated source is committed. The prerelease is published only after the pushed source commit is independently verified by the workflow.
