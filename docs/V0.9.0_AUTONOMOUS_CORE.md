# v0.9.0 Autonomous Core — Phase 1

## Purpose

Phase 1 turns the existing task/workflow foundations into a shared autonomous-operator layer. It does not replace working provider integrations and it does not add pretend executors for later phases.

The lifecycle is:

`event -> objective -> policy/capability check -> durable execution -> verification -> follow-up/recovery -> completion`

An objective is complete only when the real-world/durable postcondition is verified.

## Durable data model

The release adds only new tables; existing task, payment, banking, communication, and workflow tables are not destructively migrated.

- `va_events`: idempotent intake facts with stable event keys.
- `va_objectives`: durable VA-owned goals and state, including the count of actual user interventions.
- `va_objective_steps`: ordered execution steps with a unique idempotency key, persisted policy/capability decision, workflow reference, retry state, and verifier type.
- `va_outcome_evidence`: independently persisted evidence that a postcondition actually occurred.
- `va_follow_ups`: durable wait/follow-up state. Phase 1 persists due follow-ups but deliberately does not claim that a message was sent until the real communications executor owns it in Phase 2.
- `autonomy_metrics_daily`: objective/event/recovery metrics. The displayed autonomy percentage is derived only from completed objectives; no-data is displayed as unavailable rather than a fake 100%.

## Real executors and capability registry

The Phase-1 registry reports only capabilities already backed by shipped integrations:

- VAAPP durable workflow engine
- Google Gmail API
- Google Calendar API
- Google People/Contacts API
- Google Drive API
- Enable Banking account synchronization
- Enable Banking policy-bound payment initiation
- configured OpenAI-compatible AI provider
- configured VAAPP service connectors
- paired Android device bridge

A capability is marked live only when its real runtime connection/configuration is present. Future browser, telephony, travel, purchasing, and similar executors are intentionally absent.

## Needs You contract

`needs_user` is reserved for genuine human blockers, currently including:

- a bank/provider SCA or equivalent authorization for an already-created operation;
- provider authentication/configuration failures classified as user-required;
- an existing task explicitly marked as requiring a material decision/approval.

Routine work whose domain executor has not yet migrated into the unified objective engine is `blocked_capability`, not `needs_user`. Unknown/unsafe workflow failures are `blocked_system`, not silently retried.

## Execution and idempotency

The autonomous core dispatches real work through the existing `dispatch_intent()` -> `WorkflowRun`/`WorkflowJob` pipeline. The objective-step idempotency key becomes the workflow correlation key, so retries/repeated core cycles reuse the same durable execution rather than duplicating external actions.

The scheduled `va.core.cycle` runs every minute when automation and `va_autonomous_core_enabled` are enabled. The existing worker executes the cycle as a durable job.

## Verification and recovery

Phase 1 implements verification/reconciliation for:

- completed durable workflow runs;
- superseded workflow runs only when completed replacement jobs can be proven;
- bank payments after provider authorization/settlement;
- own-account bank transfers after provider authorization/settlement;
- previously dead-lettered workflow jobs after safe recovery;
- existing task completion/cancellation.

Transient workflow failures remain owned by the existing automatic workflow-recovery/watchdog logic. User-auth dead letters are requeued by the autonomous core only after the corresponding real provider capability is available again. Unknown failures are not blindly replayed.

## Android operations view

**Work -> Operations** shows:

- autonomy rate (or `—` until completed outcomes exist);
- active/waiting/completed objectives and event backlog;
- the strict Needs You queue;
- live/offline real capabilities and executor identity;
- recent VA-owned objectives and their evidence/step counts;
- manual `Run VA now` dispatch through the same durable autonomous path;
- recheck after unavoidable authorization.

## Phase boundary

Phase 1 is infrastructure. It does **not** mark later full-time-VA capabilities as complete. In particular, generic pending tasks/follow-ups remain durably owned but blocked until their real domain executor is implemented.

The next phase is **Phase 2 — Inbox & Communications Ownership**: event-driven Gmail/recovery sync, thread ownership, message-to-objective conversion, safe autonomous replies, durable chasing/follow-up, device messaging integration, and sent-outcome verification.
