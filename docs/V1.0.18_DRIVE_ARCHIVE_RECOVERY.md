# v1.0.18 — Drive Archive Upload Recovery & Exact-Byte Duplicate Suppression

## Defect

Document ingestion previously checked the local `documents` table before calling
Google Drive `files.create()`, but created the local `DocumentRecord` only after
Drive returned an immutable file id. If Drive accepted the upload and the response
was lost, a later sync saw no local document and could issue another archive
upload for the same bytes.

The existing Drive metadata already included `checksum_sha256`,
`account_scope`, and `va_managed=true`, but those provider properties were not
used as recovery evidence.

## Recovery contract

v1.0.18 adds a durable `DocumentArchiveUploadIntent` keyed uniquely by exact
SHA-256 plus account scope.

A fresh intent must first perform a read-only Drive lookup using the exact
provider app properties. Only the worker that atomically changes
`prepared -> submitting` may issue `files.create()`.

Once an intent is `submitting` or `creation_uncertain`, it is
reconciliation-only. A retry, worker restart, scheduler retry, or elapsed time
never authorizes another provider upload.

If exactly matching Drive evidence appears later, the original intent is bound
to that immutable Drive file id and normal local document/provenance ingestion
continues. Historical orphan files are therefore recoverable without another
upload.

If multiple historical exact-byte copies already exist, VAAPP binds the oldest
observable copy and creates no additional provider mutation. Cleanup of
historical duplicates is deliberately outside this release.

Definitive pre-create configuration or provider 4xx failures remain retryable
after the underlying capability is repaired. Ambiguous network, 409/408/429, or
provider 5xx outcomes do not become replayable.

## Human boundary

Drive archive ambiguity is a provider/system condition. It creates no Needs You
work. Google authorization remains a separate capability/authentication
boundary handled by the existing OAuth and Operational Guardian flows.
