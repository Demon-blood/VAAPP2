# Full-Time VA v0.9.3 — CRM / Relationship Memory

Phase 4 turns the existing Google Contacts directory into durable cross-channel relationship memory without inventing personal facts or merging people by name similarity.

## Identity contract

A relationship profile requires at least one concrete email or phone identity. Emails are normalized case-insensitively and phones are normalized to a stable digit representation. `RelationshipIdentity` has a global unique constraint on `(identity_type, normalized_value)`.

Display names are descriptive metadata, never identity keys. Two contacts called the same name remain separate unless a verified email/phone identity connects them. If a Google Contact or another concrete source later bridges identities that currently belong to separate profiles, the reconciler merges those profiles and writes an audit event.

## Durable memory tables

- `RelationshipMemoryState` — reconciliation attempt/success/error and aggregate counts.
- `RelationshipProfile` — canonical person plus derived relationship state.
- `RelationshipIdentity` — source-backed email/phone identities.
- `RelationshipInteraction` — idempotent interaction timeline with stable source references.
- `RelationshipFact` — factual memory with explicit provenance and confidence.

All tables are additive and compatible with the existing `metadata.create_all()` deployment strategy.

## Interaction sources

The reconciliation pass consumes evidence already owned by earlier phases:

1. Google Contacts for verified directory identities/name/organization.
2. Gmail inbound messages for inbound email history.
3. `GmailOutboundMessage` only after status is `verified`; provider-ambiguous or merely submitted mail is not counted as a confirmed outbound interaction.
4. Android `CommunicationEvent` rows for SMS and supported notification-message channels.
5. Google Calendar mirrored attendee/organizer identities for shared calendar interactions.
6. Existing `VACommunicationThread` and `VAFollowUp` rows for real waiting/follow-up state.

Every interaction is upserted by `(relationship_id, source_type, source_ref)`, so repeated scans are idempotent.

## Sensitive-message handling

When a device communication is marked protected, its raw body is not copied into relationship memory. The interaction is recorded as a protected channel interaction and the protected flag remains in structured context.

Phase 4 does not use an LLM to invent relationship facts. The factual-memory ledger currently records source-backed Google Contact fields such as display name and organization. Future learned facts must preserve the same provenance rule.

## Derived state

Profiles compute:

- primary observed email and phone;
- interaction count;
- last interaction / inbound / outbound timestamps;
- preferred channel from observed interaction frequency;
- recent topic summary from stored interaction subjects/summaries;
- bounded activity score based on observed frequency/recency;
- `waiting_on_counterparty` and `next_follow_up_at` from the existing durable communication/follow-up engine.

The score is activity, not an assertion of personal importance.

## Execution and recovery

`relationship.reconcile` is registered with the durable workflow engine and scheduled automatically. It does not depend on an external write side effect, so its postcondition is the reconciled local ledger. Provider reads remain owned by their existing Gmail/Contacts/Calendar sync jobs.

Any reconciliation error is persisted in `RelationshipMemoryState.last_error`; the workflow engine applies the standard retry/dead-letter policy. Re-running the job reconstructs the same ledger instead of duplicating memory.

## API / Android

- `GET /api/relationships/status`
- `GET /api/relationships`
- `GET /api/relationships/{id}`
- `POST /api/relationships/reconcile`

Android Work → Relationships shows memory health and profile cards. Profile details expose verified identities, source-backed facts and recent interactions. The older raw `/api/contacts` endpoint remains available for directory compatibility.

## Non-claims

Phase 4 does not claim a sales pipeline, automatic social-network enrichment, people-search scraping, or inferred sensitive traits. Browser/portal-based external enrichment belongs to later capability work and must use a real executor with the same evidence/provenance rules.
