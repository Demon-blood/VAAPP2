# v0.5.1 Financial document correctness

## Goal

Full-Time VA must distinguish **a financial event** from **a payable obligation**. An email containing a price, invoice-looking identifier, merchant name, or purchase reference is not enough to authorize a Bill or payment path.

## Financial document classes

### `payable_invoice`

Money is still owed. A payable classification requires outstanding-payment evidence such as an amount due, payment due, due date, outstanding balance, payment request/instructions, overdue language, or invoice evidence combined with a due date/IBAN.

Only this class may retain a structured `bill` decision and enter the bill lifecycle.

### `paid_receipt`

The source represents a completed purchase/payment. Examples include purchase receipts, payment confirmations, successful charges, order confirmations, Google Play GPA purchases, App Store receipts, PayPal confirmations, Stripe receipts, Amazon purchase confirmations, and card purchase confirmations when no outstanding-payment evidence is present.

Paid receipts:

- do not create Bills;
- do not request creditor approval;
- do not expose Process payment;
- do not enter auto-pay;
- are archived/labeled as financial evidence;
- are stored in `financial_records`;
- can optionally be reconciled with a real bank transaction.

### `statement_or_notice`

The source is financial information but does not establish an outstanding payable obligation. It is preserved as a financial record and cannot enter the payment engine.

## Google Play / Google Commerce handling

A `GPA.1234-5678-9012-34567` identifier in normal Google Commerce / Google Play purchase mail is a high-confidence paid-receipt signal. Explicit outstanding-payment language still takes precedence; the implementation does **not** globally whitelist Google as non-payable.

This prevents Google Play purchases and subscription renewals from appearing as unpaid Google Commerce Limited bills merely because the message contains an amount and a GPA identifier.

## Historical correction

At backend startup and during durable housekeeping, v0.5.1 scans existing non-terminal bills conservatively.

When strong evidence shows that an old Bill is actually non-payable:

1. the Bill row is retained but becomes `reclassified_nonpayable`;
2. the reason records the correction;
3. a `financial_records` row is created;
4. bill/creditor/funding exception tasks are completed;
5. the saved email decision has its `bill` removed and its financial document type corrected;
6. the email action flag is cleared when no unrelated action remains;
7. an audit event records the original and corrected classification.

If a non-terminal Payment already exists for that Bill, automatic reclassification is blocked and audited instead of hiding an in-flight banking action.

## Bank transaction reconciliation

Paid receipts may be matched against transactions from the already-connected Enable Banking accounts. Matching requires a unique combination of:

- exact absolute amount;
- compatible currency;
- close transaction date;
- provider text and/or the order reference.

A match only updates the receipt's reconciliation metadata. It never initiates a transfer, changes a bank balance, or marks a Bill paid.

## Subscription linkage

If AI already returned a structured subscription, the receipt links to that subscription. If AI did not, deterministic fallback creates subscription data only when the source explicitly identifies both recurring billing and the specific product/plan/service. It deliberately refuses to create a generic provider-level subscription that could merge unrelated purchases.

## API

Authenticated endpoints:

- `GET /api/financial-records`
- `GET /api/financial-records?record_type=paid_receipt`
- `POST /api/financial-records/reconcile`

The existing `GET /api/bills` endpoint excludes `reclassified_nonpayable` historical rows while keeping them in PostgreSQL for auditability.

## Android

Money has four tabs:

1. Bills
2. Payments
3. Accounts
4. Receipts

Receipts are explicitly marked as non-payable. The Bills screen only exposes **Process payment** for Bills whose backend status is `validated`.

## Migration behavior

The release adds one table only:

- `financial_records`

No existing table column is changed. The current SQLAlchemy `metadata.create_all()` startup behavior creates the new table additively.
