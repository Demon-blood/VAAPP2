# v0.9.5 Documents / Forms / Deadlines — Phase 6

Phase 6 turns documents from passive archive entries into durable VA-owned obligations. It reuses the existing Gmail ingestion, Google Drive archive, Autonomous Core, workflow engine, relationship/calendar context, and the Phase-5 secure browser rather than introducing a parallel document or form runtime.

## Operating contract

A document does not become "done" because it was downloaded, parsed, or because a submit button was clicked. The Phase-6 path is:

`provider document -> source-backed intelligence -> exact obligation -> capability/policy check -> durable execution -> provider verification -> completion evidence`

The VA owns an actionable obligation until one of these terminal states is proven:

- the required provider postcondition is verified;
- the source obligation is cancelled/superseded by evidence;
- the obligation is explicitly blocked by a missing executor (`blocked_capability`);
- the provider outcome is unsafe to retry and requires reconciliation (`blocked_system`);
- authentication, a protected/material decision, or information only the account holder can supply creates a genuine Needs You state.

## Durable data model

Phase 6 adds only additive tables so existing deployments can continue to initialize with SQLAlchemy `metadata.create_all()`.

### `DocumentIntelligence`

One intelligence record per archived `DocumentRecord` stores:

- the document/source checksum used for idempotent re-analysis;
- SHA-256 of the extracted text;
- encrypted extracted text;
- detected document type;
- exact deadline candidates and discovered form URLs;
- protected-document classification;
- analysis state/error and timestamp.

The original provider file remains authoritative. Extracted text is working intelligence, not a replacement source of truth.

### `DocumentObligation`

An actionable deadline/form becomes a durable obligation with a unique correlation key, source document, issuer/title, obligation type, exact due time, form URL, priority, protected/material flags, current state, and links to the VA objective, secure portal operation, and form-submission ledger.

An obligation is still owned when it is blocked. A missing executor therefore becomes `blocked_capability` rather than silently disappearing from the user's workload.

### `FormSubmission`

Every form attempt has a stable idempotency key, encrypted exact field values, the field-key list, portal/browser-operation references, material-approval state, execution state, and provider verification timestamp. The encrypted payload means sensitive form values are not copied into plain audit/event metadata.

### `UserProfileFact`

Reusable account-holder facts are stored encrypted with a value hash, provenance and verified flag. Google OAuth may seed verified name/email facts; explicitly provided facts override inferred/synced values. Forms only receive facts that are actually present and verified.

## Real document extraction

### Google Drive

The document intelligence worker downloads the archived Drive file bytes using the real Google Drive API and `MediaIoBaseDownload`. The current intelligence limit is 12 MB per file to keep background processing bounded.

### Gmail source reconciliation

For Gmail-origin records, Phase 6 can retrieve the real source message and extract its actual plain/HTML message body. This allows deadline/form ownership to be reconciled to provider evidence rather than only the archive filename.

### PDF and text formats

PDF text uses native PyMuPDF extraction. HTML is converted to visible text with Beautiful Soup. Plain text is decoded deterministically. Phase 6 deliberately does **not** advertise OCR: image-only/scanned documents without machine-readable text remain unsupported by this executor and must not be treated as successfully understood.

## Exact deadline policy

Deadline extraction is deliberately conservative.

Recognized exact dates include forms such as:

- `2026-09-21`
- `21/09/2026`
- `21-09-2026`
- `21.09.2026`
- Dutch/English month-name dates such as `21 september 2026` or `21 September 2026`

A date is promoted only when nearby source text contains a real deadline/expiry/submission/response signal (for example *deadline*, *due*, *submit by*, *respond by*, *uiterlijk*, *ten laatste*, *indienen vóór*, *vervaldatum*). A date without a year is not guessed. Ordinary dates in statements or correspondence are not automatically treated as deadlines.

Date-only deadlines are represented as the end of that source calendar day, avoiding an accidental midnight deadline.

## Form discovery and trust boundary

Phase 6 can discover HTTPS form URLs from document text, but discovery does not grant execution authority. A form may be executed only when its host matches an already configured `BrowserPortal` and that portal's explicit allowed-host list.

This preserves the Phase-5 security boundary:

- HTTPS only;
- explicit host allowlist;
- private/loopback/link-local targets blocked;
- DNS rebinding/private-network resolution blocked at runtime;
- main-frame redirect host enforcement;
- encrypted credentials/session state;
- CAPTCHA never bypassed;
- OTP/MFA can become Needs You and resume the same durable session.

A link in a PDF/email never silently creates a trusted portal.

## Fill-before-submit safety

Form execution is split into two different browser actions:

1. `autofill_form` — replay-safe and explicitly non-side-effecting;
2. `click_action` — the separately persisted potentially mutating submit action.

The autofill step maps verified profile facts to common label/name/placeholder aliases. Before the submit step, the executor checks visible required controls. If required information is missing, execution stops with `form_input` Needs You **before any submit side effect**.

This separation prevents a missing address, phone number, date of birth, reference, or similar account-holder fact from being misclassified as an ambiguous provider submission.

## Material commitments

Phase 6 does not weaken the Phase-5 material-action boundary. Browser operations that would submit a payment, purchase, contract acceptance/signature, account-security change, account closure/deletion, or comparable material commitment still require the existing specific one-time approval before the mutating action executes.

Routine reversible form submissions may execute automatically when policy and portal capability allow them.

## Ambiguity and idempotency

The form-submission record and browser operation are persisted before provider execution. The submit click is marked non-replay-safe. If the provider response is ambiguous after the side effect, VAAPP does not click again simply because a worker retried.

Instead, the existing browser-operator ambiguity model applies: reconcile the declared provider postcondition. If it cannot be proven, keep the work blocked rather than risking duplicate submissions.

## Provider verification and completion

A form obligation completes only after its linked browser operation reaches `verified` and the declared provider postcondition is independently observed. Phase 6 uses provider-success text postconditions such as a confirmed receipt/submission page, with the actual browser evidence retained by the Phase-5 browser ledger.

`DocumentObligation.completed_at` is therefore derived from the verified provider operation, not from the time the VA attempted the submit.

For obligations without a safe executable portal, the VA records a `document_obligation_blocked` event. The Autonomous Core turns that event into a deadline-bearing `blocked_capability` objective so the obligation remains visible and VA-owned.

## Background reconciliation

The workflow engine has a durable `documents.reconcile` job. Existing six-hour document housekeeping also invokes document ownership reconciliation, allowing the system to:

- analyze newly archived documents;
- create/update obligations idempotently;
- link form submissions to secure browser operations;
- observe browser verification/auth/ambiguity outcomes;
- repair status after restart;
- mark overdue obligations without pretending they are completed.

The API/UI can also request an immediate reconciliation without replacing the durable background path.

## API surface

Authenticated Phase-6 endpoints include:

- `GET /api/documents/ownership/status`
- `GET /api/documents/obligations`
- `GET /api/documents/obligations/{id}`
- `POST /api/documents/reconcile`
- `GET /api/documents/profile-facts`
- `PUT /api/documents/profile-facts`

Profile-fact values are accepted only through the authenticated device API and stored encrypted.

## Android experience

Work → **Documents** remains the single document workspace. Above the existing archive it now shows:

- obligation count and ownership health;
- verified reusable profile-fact count;
- next exact deadline;
- obligation type/status/due date;
- protected/material flags;
- blocked/error reason;
- an immediate reconcile action;
- an authenticated path to add a missing verified profile fact.

The screen reports the actual backend state; it does not offer a manual “mark submitted” shortcut.

## Validation gate

The Phase-6 local contract covers:

- release identity `0.9.5` / Android `0.9.5+38`;
- additive encrypted document/form/profile ledgers;
- real Drive/PDF/Gmail source extraction paths;
- exact deadline signals and refusal to guess partial dates;
- fill-before-submit separation;
- provider postcondition requirement;
- completion only after verified browser evidence;
- durable workflow integration;
- VA-owned `blocked_capability` objectives;
- API and Android wiring.

Local static/compile validation is not the release gate. Phase 6 is complete only after the extracted overlay is committed to `main` and the repository's full GitHub Actions backend + Flutter + Android release workflow succeeds.
