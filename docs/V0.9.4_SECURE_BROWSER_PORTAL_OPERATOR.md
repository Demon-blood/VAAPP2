# Full-Time VA v0.9.4 — Secure Browser / Portal Operator

Phase 5 gives VAAPP a real browser executor for web portals that do not expose a suitable API/connector. The browser is a provider executor inside the existing autonomy/workflow architecture; it is not a parallel automation engine.

## Execution contract

A portal operation is persisted before Chromium runs. The durable record contains a stable idempotency key, current step, side-effect dispatch state, encrypted exact plan, encrypted verification rule, provider/session state, challenge state and evidence references. The Autonomous Core owns the higher-level objective through a `browser_operation` step.

Completion requires an explicit postcondition observed on the provider page. Supported postconditions include URL/title/text checks and selector presence/absence. A successful navigation, click, fill or form submit is not sufficient evidence by itself.

## Navigation and SSRF protection

Portal base/login URLs must use HTTPS and cannot embed credentials. Each portal stores an explicit allowed-host set. Direct localhost, private, link-local, multicast, reserved and local/internal hostnames are rejected. During execution, VAAPP also resolves request hostnames and blocks addresses that resolve into those protected network ranges. Main-frame navigation/redirects are restricted to the portal host allowlist.

## Secret/session handling

Portal usernames/passwords and Playwright storage state are encrypted with the existing VAAPP Fernet key. Exact operation plans, verification values, resume URLs, one-time OTP resume values and screenshot evidence payloads are encrypted as well. Public operation summaries omit raw secrets and screenshot responses are authenticated and marked `no-store`.

## Ambiguous side effects

Clicks and Enter-key actions are treated as potentially mutating by default unless explicitly marked replay-safe. Before a non-replay-safe side effect, VAAPP commits `dispatching` and the step index. If the worker crashes or the provider response is ambiguous, VAAPP first checks the operation postcondition. If the postcondition is proven, it records verified completion. If not, the operation becomes `creation_uncertain`; it is not blindly replayed.

## Authentication challenges

CAPTCHA is detected and never bypassed. OTP/MFA or external approval challenges become `needs_user_auth`, preserving encrypted session state. An OTP supplied through the Android Portals surface is encrypted as a one-time resume value and cleared after use. External approval can be rechecked against the same durable operation.

## Material commitments

Browser plans that pay/purchase, transfer/withdraw, sign or accept contracts, close/delete accounts, change passwords/security settings, or perform comparable material commitments require a specific one-time approval. This approval is tied to the durable BrowserOperation and does not weaken the global policy for unrelated work.

## Runtime

The backend installs Playwright and its Chromium/system dependencies during the container build and runs as the non-root `vaapp` user. If Chromium is absent at runtime, the operation is reported as `blocked_capability`; VAAPP never substitutes a simulated result.

## API and Android

Phase 5 exposes browser status, portal configuration, encrypted credential update, operation list/detail, OTP submission, external-auth resume, material approval, and authenticated evidence endpoints. Work → **Portals** exposes these states while reserving Needs You for unavoidable authentication/CAPTCHA or the material decision itself.

## Verification gate

The Phase-5 overlay includes static release/security contracts and Python compilation checks. The phase is not complete until the package is committed to `main` and the repository GitHub Actions pipeline passes backend tests, Flutter analysis/tests, Android release build/signing and prerelease publishing.
