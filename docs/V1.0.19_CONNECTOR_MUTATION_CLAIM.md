# v1.0.19 — Scheduled Connector Mutation Claim & Retry Integrity

## Defect

Scheduled connector rules run through the generic connector executor. That executor can
perform external mutations including REST POST/PUT/PATCH/DELETE, webhooks, Telegram
messages, SMTP sends, WebDAV uploads, SFTP uploads, OAuth-backed writes, and arbitrary
Browserless function/BQL work.

Before v1.0.19, a provider timeout, connection reset, HTTP 408/409/425/429, or 5xx could
escape from the connector rule as a transient workflow failure. The durable workflow
engine was then allowed to retry the whole `connectors.rules.run` job. If the provider
had accepted the first mutation but its response was lost, that retry could repeat the
external side effect.

## Dispatch claim

v1.0.19 adds `ScheduledConnectorMutationIntent`, an additive ledger keyed by automation
rule plus deterministic scheduled occurrence.

Each external mutation is prepared durably and then must win an atomic
`prepared -> submitting` transition before the generic connector executor is called.
The claim and the rule's `last_run_at` are committed before provider dispatch.

Only the worker that wins that transition may mutate the provider.

## Ambiguous outcome

Once dispatch has been claimed, any exception from the generic connector execution is
treated conservatively as `execution_uncertain`.

That occurrence is not routed through normal transient workflow retry. It creates no
Needs You task and cannot be dispatched again. A scheduler retry, worker retry, process
restart, elapsed time, timeout classification, or manual Autopilot recovery does not
authorize replay of that occurrence.

The state remains VA-owned because the generic connector contract does not provide a
provider-independent postcondition that could safely prove whether an arbitrary webhook,
message, upload, or API mutation took effect.

## Recurring rules

This release does not disable legitimate recurrence. The scheduler continues to create
fresh connector-rule work every minute, and a later interval bucket represents a new
scheduled occurrence. A previous ambiguous occurrence does not authorize replay of
itself, but it also does not permanently block future independently scheduled occurrences.

Read-only connector operations retain their existing bounded transient retry behavior.

## Legacy retry quarantine

Pre-v1.0.19 `connectors.rules.run` jobs already in `running`, `retry`, or `dead_letter`
state lack a durable mutation claim. On the first v1.0.19 startup those jobs are
superseded fail-closed instead of replayed. The normal one-minute scheduler supplies
fresh work afterward.

This may conservatively discard a historical read-only retry mixed into that generic
job type, but it prevents an unknowable pre-upgrade provider mutation from being repeated.

## Human boundary

Provider response loss is not a human decision. It remains system/VA-owned and does not
become fake Needs You work. Genuine connector authentication/configuration issues on
read-only or pre-dispatch validation paths remain governed by existing capability rules.
