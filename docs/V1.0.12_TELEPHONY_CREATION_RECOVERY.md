# v1.0.12 — Telephony Creation Recovery & Retry Integrity

v1.0.12 closes the remaining ambiguity gap in outbound Twilio call creation.

VAAPP already persists a durable call intent before the irreversible Twilio `POST /Calls.json` and suppresses blind creation retry when the response is lost. Before v1.0.12, however, an intent could remain `creation_uncertain` indefinitely when both the create response and the normal signed callback carrying the `CallSid` were missed.

## Recovery contract

For an outbound `creation_uncertain` call that has no `CallSid`, VAAPP queries Twilio's authenticated Calls resource using the exact encrypted source/destination numbers and a bounded creation-date window. Candidate acceptance is deliberately stricter than Twilio's day-granularity filters:

- exact normalized `To` number;
- exact normalized `From` number;
- Twilio direction exactly `outbound-api`;
- provider `date_created` or `start_time` within ten minutes of the durable VAAPP creation/start timestamp;
- a non-empty provider `CallSid` not already bound to another VAAPP call intent.

Exactly one candidate is required. A unique candidate is bound to the existing `TelephonyCall`, recorded as `provider_create_recovered` evidence, and reconciled through the existing provider-status state machine. No new call intent is created.

Zero candidates remain `creation_uncertain` and VA-owned. Multiple candidates remain `creation_uncertain` and VA-owned. Provider lookup failure also remains VA-owned. None of those states creates a Needs You task or redials the number.

## Retry integrity

A follow-up call attempt may be created only after the parent call has a real provider `CallSid` and Twilio reports a terminal provider status. A scheduled retry therefore cannot race an active call, an unbound ambiguous creation, or delayed provider status delivery.

Material payment, legal, medical, binding-commitment, and authentication/security boundaries during an actual voice conversation are unchanged and remain the existing genuine human boundary.

No database schema migration is required; recovery evidence uses the existing `TelephonyEvidence` ledger.
