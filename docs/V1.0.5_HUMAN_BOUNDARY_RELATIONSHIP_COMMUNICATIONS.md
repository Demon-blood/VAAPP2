# Full-Time VA v1.0.5 — Human Boundary & Relationship-Aware Communications

v1.0.5 tightens the boundary between autonomous work and genuine user decisions. It replaces ambiguous “recheck after authorization” handling for material VA-owned decisions with objective-bound Authorize/Decline actions, repairs duplicate communication ownership at the source/correlation layer, and adds explicit person-specific reply preferences on top of the existing Phase-4 relationship memory.

## Specific authorization contract

A material decision exposed in **Needs You** carries an `action_fingerprint` derived from the exact objective and proposal. The Android client must submit the same fingerprint when authorizing or declining. If the source proposal changed, the backend rejects the decision and requires a refresh.

Authorization is recorded in the objective audit/context and is **not outcome evidence**. It never creates `VAOutcomeEvidence` and never marks an external objective completed. After authorization, the state machine resumes immediately:

- an approved saved Gmail reply is converted into the existing durable Gmail reply objective, including provider reconciliation;
- an approved SMS reply becomes a pending device `CommunicationAction`, which still needs Android/carrier evidence;
- if no real executor exists for the authorized action, the objective becomes `blocked_capability` instead of pretending the action occurred.

Decline cancels the specific decision/objective and linked legacy task projection where applicable. It does not delete the original message/evidence.

Provider authentication/SCA/MFA remains a different kind of Needs You item. It is never replaced by a local “Authorize” button. When a safe HTTPS authorization URL is available, the Needs You card offers **Open provider authorization**; after the user completes the bank/provider flow, **Recheck after authorization** resumes reconciliation. If no URL is available, the card keeps the provider/manual guidance and recheck path.

## Communication ownership and duplicate repair

Communication events already have a Phase-2 durable ownership path. Legacy `Task(source_type="communication")` rows are treated as projections and no longer seed a second VA objective.

The maintenance repair cancels older task-derived duplicate objectives. A protected message by itself is **not** treated as an authorizable action: without a concrete safe proposal it remains VA-owned (`blocked_capability`) rather than becoming a fake approval task. A source communication objective becomes `needs_user` only when a concrete reply proposal is subject to an explicit relationship-level review requirement (or a future protected proposal is explicitly modeled).

Android can expose the same SMS twice: once through the native SMS receiver and once through a Google Messages or Samsung Messages notification. v1.0.5 correlates only this known cross-transport pair within a bounded time window and matching message content. Same-channel identical messages are never collapsed merely because their text matches. Original source evidence is retained; duplicate ownership is superseded rather than deleted.

## Relationship-aware reply preferences

Person-specific preferences reuse the existing `RelationshipProfile` / `RelationshipIdentity` / `RelationshipFact` model. Explicit settings are stored as a provenance-backed `RelationshipFact` with `source_type=user_explicit`; no parallel contact database is introduced.

Editable preferences include language, tone, formality, greeting/sign-off style, reply length, preferred channel, relationship category (including partner), explicit instructions/examples, routine auto-send preference, topics that always require approval, and explicit per-channel display-name aliases for notification-driven apps.

Gmail/SMS normally resolve relationships through verified email/phone identities. WhatsApp, Messenger, Telegram and Signal notifications may expose only a display name, so v1.0.5 never merges that name automatically. The user can explicitly bind the exact displayed name to a relationship for that channel; ambiguous duplicate aliases resolve to no relationship rather than guessing.

Resolution order is:

`global communication defaults -> learned relationship writing style -> explicit relationship override -> current thread/message context`

Relationship matching uses verified email/phone identities, never name-only matching. Explicit user settings and examples override learned style. Sensitive personal attributes are not inferred.

### Learned writing style

A relationship can opt in to **Learn how I write to this person**. v1.0.5 builds the profile only from device-observed outgoing history after excluding known VA-generated sends. The current verified historical source is Android's SMS sent/outbox provider (`android_sms_history`), which records both direction and the actual sent body. Incoming messages are never style samples. Messages generated by a successful VA `CommunicationAction` are excluded from later SMS-history learning so the system does not train on its own output. Protected messages, credential/security-code-like content, long account/card/IBAN-like number sequences and link-bearing samples are also excluded.

At least three safe samples are required before learned style is supplied to the model. The stored aggregate contains bounded traits such as average message length, lowercase-start tendency, punctuation/question/exclamation ratios, line-break use, emoji tendency/common emojis, source-channel counts and up to five short representative examples. It is stored as a provenance-backed `RelationshipFact` (`fact_key=learned_communication_style`, `source_type=verified_user_outbound_aggregate`). Raw source messages are not copied into audit logs.

The learned profile is relationship-level and therefore can inform drafting on Gmail, SMS, WhatsApp, Signal, Telegram, Messenger and supported Messages notifications once the current sender resolves to that relationship. Notification-only apps do **not** currently expose historical user-sent chat messages through Android's notification listener; for a Messenger/WhatsApp/Telegram/Signal-only relationship, explicit examples remain the reliable bootstrap until a real sent-history/provider integration exists. The VA never pretends incoming chat history proves how the user writes.

### Authority separation

Style and relationship settings never grant financial, legal, browser, banking, credential, payment or other material execution authority. Existing deterministic safety gates remain authoritative. `routine_auto_send=true` can only allow a reply that has already passed those gates. `routine_auto_send=false` and configured approval topics can make policy stricter.
