# VAAPP v0.9.8 — Purchasing / Travel / Logistics / Customer Service

Phase 9 turns the existing order, support, Secure Browser, telephony and autonomous-objective foundations into one durable fulfillment subsystem. It does not claim universal merchant or travel-site automation: a real provider executor must be configured before VAAPP can act externally.

## Durable ownership

`FulfillmentProvider` stores an encrypted provider recipe, optional Secure Browser portal link, optional encrypted verified support number, scope and provider type. `FulfillmentRequest` owns one objective such as purchase, travel booking, tracking, return, refund, cancellation or customer-service resolution. `FulfillmentAction` is the persisted external-action intent. `FulfillmentEvidence` records observed completion/authentication/authorization evidence without exposing encrypted request details in audit logs.

Existing `OrderRecord` and `SupportCase` rows are reconciled into fulfillment requests with stable idempotency keys. A delivery/support record that is already terminal can provide completion evidence. Otherwise the VA owns the objective until provider evidence satisfies it.

## Provider execution

Browser fulfillment uses the existing allowlisted HTTPS Playwright executor. Provider recipes supply exact steps and an explicit postcondition. Recipe variables come from the encrypted fulfillment request and linked order metadata. The browser operator continues to block localhost/private-network targets, host escapes, CAPTCHA bypass, and blind replay after ambiguous side effects.

Customer-service work may instead use the configured Twilio support number. The telephony executor remains responsible for signed callbacks, bounded retries, automated-assistant disclosure and counterparty outcome verification.

If no real executor is configured for the chosen provider/action, the request becomes `blocked_capability`. VAAPP does not manufacture a completion record.

## Spending authority

Purchase and travel browser workflows are material commitments. Phase 9 adds optional standing preauthorization, configured separately for purchases and travel:

- enable/disable standing authorization;
- maximum one purchase/travel commitment in EUR;
- aggregate monthly purchasing/travel commitment limit in EUR.

Standing authorization applies only to a known positive EUR amount. The request must fit the relevant single limit and the monthly commitment envelope. If any condition is missing or exceeded, the request becomes `needs_user` before provider dispatch.

A specific one-off payment authorization also requires the request to contain a known positive EUR amount. That authorization is recorded as `specific_payment_authorization` evidence. Bank/card/provider SCA, OTP, MFA or other authentication remains a separate provider-required `needs_user` step.

The fulfillment service may set the linked browser operation's material authorization timestamp only after either standing policy or specific authorization has been established. Audit/evidence records state the authorization basis instead of pretending that the user manually approved every in-policy action.

## Ambiguity and idempotency

Every fulfillment request and action has a stable idempotency key. The `FulfillmentAction` row is committed before browser preparation or a telephony provider call. A linked browser operation is reused by idempotency key across restart/reconciliation.

If the browser reports `creation_uncertain`, Phase 9 records `blocked_system` and does not issue another side effect. Telephony uses its existing ambiguity-safe call ledger. Successful provider dispatch alone never completes a fulfillment objective.

## Logistics and customer-service reconciliation

The scheduler runs fulfillment reconciliation every five minutes. It imports newly detected orders/support cases, attaches newly configured providers, reconciles browser/call state, follows waiting provider outcomes, and records terminal source evidence.

A Twilio call that ends without verified counterparty outcome leaves the fulfillment request waiting and schedules later follow-up rather than declaring success. A browser action completes only after the configured postcondition has been independently verified.

## Android workspace

The Fulfillment workspace is opened from the main app bar. It shows ownership counts, configured providers and request states; permits creation of fulfillment objectives and provider recipes; exposes explicit one-off payment authorization when required; and can trigger reconciliation. The screen explicitly states that browser/payment intent is not completion evidence.
