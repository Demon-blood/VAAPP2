# Full-Time VA v1.0.4 — Execution Readiness & Setup Assistant

v1.0.4 addresses a recurring real-world problem in the v1 line: a capability could correctly report **OFFLINE** while the product still forced the user to infer which provider setting, consent, executor, or linkage was missing. This release keeps the same executor/evidence model and adds explicit readiness diagnostics plus in-app setup entry points.

## Capability setup contract

Every capability may expose:

- `available`: whether the currently shipped real executor can be used.
- `readiness`: `offline`, `ready`, or `live`.
- `verified`: optional end-to-end provider evidence, used where a configured executor can exist before real delivery has been observed.
- `detail`: the current missing prerequisite or verified executor state.
- `setup.destination`: where configuration belongs.
- `setup.steps`: capability-specific setup guidance.
- `setup.action`: the Android destination/action that can safely be opened from Work → Operations.

Setup metadata is deliberately non-secret. API keys, passwords, bank credentials, Pub/Sub verification tokens, browser credentials and other secret material are never returned by the capability matrix.

## Gmail Pub/Sub readiness

Gmail read/send continues to depend on the normal Google OAuth connection.

Real-time Gmail notifications are stricter. `gmail_push` is available only when all of the following are true:

1. a live Google OAuth connection exists;
2. `google_pubsub_topic` is configured;
3. `google_pubsub_verification_token` is configured;
4. the durable `GmailMailboxState` contains a non-expired Gmail watch;
5. the active watch is bound to the currently configured topic.

An accepted Gmail watch without an observed Pub/Sub delivery is reported as **READY**. A real Pub/Sub callback recorded by the mailbox state upgrades the display to **LIVE**. The distinction prevents a topic string or accepted Gmail watch from being misrepresented as proven end-to-end push delivery.

The Android setup sheet constructs the callback from the paired backend URL:

`<paired-backend>/api/google/pubsub?token=<the same private verification token stored in Services>`

The token value itself is never returned by the capability endpoint.

**Activate watch** calls the existing authenticated `POST /api/google/watch` endpoint. It can establish/renew the Gmail watch, but it never fabricates the later Pub/Sub delivery evidence.

## Fulfillment readiness

Older readiness logic could combine unrelated configuration: one enabled fulfillment provider plus some unrelated enabled browser portal was enough for the broad capability to look available.

v1.0.4 requires a provider-specific executor relationship. At least one enabled provider must have either:

- its own `browser_portal_id` linked to an enabled Secure Browser portal; or
- a configured support phone while autonomous telephony is genuinely live.

This does not guarantee that every action type has a recipe. Individual objectives still enter `blocked_capability` when their provider/action recipe is absent.

## Android setup assistant

Work → Operations capability rows are tappable. The sheet shows:

- the current readiness state;
- why the executor is unavailable or what executor is active;
- the setup destination;
- numbered capability-specific steps;
- a direct action when one is safe.

Supported direct setup destinations include Services, Communications Autopilot, Calls, Fulfillment, and the Work → Portals tab.

The UI explicitly repeats the completion rule: configuring an executor, activating a Gmail watch, or reaching READY/LIVE is not evidence that an external objective completed. Domain-specific provider/source evidence remains mandatory.
