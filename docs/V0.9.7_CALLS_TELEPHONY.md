# v0.9.7 Calls / Telephony

Phase 8 gives VAAPP a real telephone executor. Android call screening remains useful for deciding whether an incoming device call should ring, be silenced, or be blocked, but it is not a conversation executor. Autonomous PSTN conversations use Twilio Programmable Voice and are owned in the same durable objective/evidence model as the rest of VAAPP.

## Provider configuration

Configure the **Twilio Programmable Voice** section in VAAPP Settings with:

- Twilio Account SID;
- Twilio Auth Token;
- a Twilio voice-capable caller number in E.164 format;
- optional owner/display name used in the automated-assistant disclosure;
- speech language, maximum turns, maximum call duration, and bounded maximum attempts.

For calls to the Twilio number, configure its Voice webhook as:

`POST <PUBLIC_BASE_URL>/api/telephony/twilio/incoming`

Outbound voice and status callback URLs are generated per durable call intent. Secrets and full phone numbers are not written to source code.

## Durable call ownership

`TelephonyCall` is created before any outbound provider POST. The row contains a stable idempotency key, attempt series, encrypted call purpose/expected outcome, encrypted phone details, a hashed/encrypted webhook token, provider state, verification state, retry state, and links to the owning VA objective/step.

`TelephonyTurn` stores each counterparty/VA speech turn encrypted at rest plus a content hash and provider/logical turn reference. `TelephonyEvidence` stores idempotent provider callback/reconciliation evidence without copying phone numbers or transcript bodies into audit metadata.

A phone call can therefore survive process restarts without losing whether it was merely planned, dispatched, ringing, connected, provider-completed, objectively verified, blocked, or awaiting a bounded retry.

## Creation ambiguity and retries

The call intent is committed before the Twilio Call-resource request. If that request times out or the network fails after Twilio might have accepted it, VAAPP marks the intent `creation_uncertain` and suppresses automatic creation retry.

The per-call webhook token already sent in the provider request can bind a later signed voice/status callback back to the durable intent and recover the `CallSid`. If no provider identity/evidence arrives, the intent remains reconciliation-only. VAAPP does not solve uncertainty by dialing the number again.

Clear provider outcomes such as `busy` or `no-answer` may schedule a later bounded attempt when attempts remain. Each later attempt is a new child call with its own deterministic idempotency key; it never replays the original ambiguous provider operation.

## Signed provider callbacks

Incoming-call, voice-control, speech-turn, and status endpoints are public only because Twilio must reach them. Every one validates `X-Twilio-Signature` against the exact externally configured callback URL and the received form parameters before any call state is changed.

Device management endpoints remain protected by the paired-device bearer token.

## Conversation policy

Every conversation identifies VAAPP as an automated virtual assistant. The call engine can autonomously:

- gather routine information;
- take and clarify messages;
- ask about availability;
- chase an ordinary status;
- collect a reference number;
- coordinate low-risk logistics that do not create a material commitment.

It must not accept or create payments, purchases, contracts, debt admissions, legal settlements, medical decisions, employment commitments, credential/security changes, identity-verification steps, or disclosure of passwords, PINs, OTP/2FA codes, card details, or bank credentials. A deterministic phrase gate and the structured voice decision policy both stop the call and set `needs_user` when a material/authentication step is reached.

Call recording is not enabled. The speech text needed to operate the conversation is encrypted in the VAAPP database.

## Objective verification

Provider state and objective state are intentionally separate.

A provider status such as `completed` proves only the provider call lifecycle. It does not prove that the intended person answered or that the requested outcome occurred. Without explicit counterparty evidence the call becomes `provider_completed_unverified` and the VA objective remains waiting/verifying.

Only an actual counterparty statement that clearly confirms the expected outcome may set `objective_satisfied=true`. VAAPP then stores `telephony_counterparty_confirmation` as outcome evidence and completes the objective. Later provider callbacks cannot erase an existing `needs_user` handoff.

## Bounded operation

The configured turn count is clamped to 2–20 turns and call duration to 60–1800 seconds. If either boundary is reached without verified completion, VAAPP ends the call and either schedules one bounded later attempt or leaves the objective verifying.

A one-minute reconciliation loop:

1. quarantines stale pre-provider/dispatch call intents as `creation_uncertain`;
2. refreshes active known `CallSid` states from Twilio;
3. starts only retries that were already explicitly scheduled and remain within the attempt limit.

## Android Calls workspace

The Android **Calls** destination displays provider readiness, caller-number masking, active call state, provider status, objective verification, attempt count, retry timing, encrypted transcript/evidence details, and a provider reconciliation action.

When a manual call request loses its HTTP response, the app keeps the same draft idempotency key in secure local storage for a retry, including across an app restart. The backend therefore returns/reconciles the existing call intent instead of interpreting a second tap as a new call.

## Completion contract

Phase-8 work is complete only when all of the following are true:

1. a real provider call intent exists;
2. the external provider lifecycle is reconciled through signed callbacks and/or provider GET state;
3. the expected outcome is supported by counterparty evidence when objective completion is claimed;
4. ambiguous creation has not been blindly retried;
5. material/authentication decisions remain with the user;
6. retries, if any, remain bounded and durable.
