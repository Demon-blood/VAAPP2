# Full-Time VA v0.6.2 — Gmail Conflict Hardening

## Live failure addressed

The Render deployment built and started v0.6.1 successfully, but durable `gmail.sync` jobs could fail while creating a Gmail label with HTTP 409 `Label name exists or conflicts`. The v0.6.1 resolver re-listed labels after a conflict, but still required an immediately visible exact display-name match. Live Gmail behavior showed that the conflicting label may not become visible quickly enough for that exact match.

## v0.6.2 behavior

- Label names are reconciled using exact matching first, then conservative Unicode NFKC + trim + casefold comparison.
- A missing label is created only once. After HTTP 409, the VA re-lists labels with bounded backoff instead of repeating the conflicting POST.
- If Gmail eventually exposes an equivalent label, its immutable label ID is used.
- If Gmail still does not expose an ID after bounded reconciliation, only that cosmetic label is skipped. The email's substantive automation continues and the durable `gmail.sync` job does not fail for that label conflict.
- Message mutation is skipped entirely when there are no resolved labels or removals to apply.
- Non-409 Google errors continue to propagate into the durable retry/provider-recovery machinery.
- Startup retires pre-v0.6.2 retry/dead-letter jobs with this exact label-conflict signature, then the scheduler immediately enqueues a fresh Gmail sync.
- Scheduler startup now uses a timezone-aware `Europe/Brussels` timestamp, fixing the exact two-hour CEST misfire visible in the Render log.

## Safety boundary

This hotfix does not suppress OAuth, permission, authentication, provider 5xx, rate-limit, or message-mutation failures. It only degrades an unresolved label-name conflict because a label is organizational metadata and restarting the complete mailbox workflow cannot resolve a persistent cosmetic naming collision safely.
