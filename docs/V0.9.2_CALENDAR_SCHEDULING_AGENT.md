# Full-Time VA v0.9.2 — Calendar & Scheduling Agent

Phase 3 converts the existing Google Calendar integration from convenience calls into an owned autonomous executor.

## Operating contract

Calendar work follows the same durable lifecycle as the rest of VAAPP:

`Observe -> Own objective -> Check policy/capability -> Persist mutation -> Execute -> Verify provider state -> Follow up/recover -> Reconcile -> Complete`

A Google API response is not sufficient proof of completion. A calendar objective completes only after the provider event is independently observed in the requested state.

## Durable calendar state

Three additive tables are introduced:

- `CalendarSyncState` stores calendar synchronization health and timestamps.
- `CalendarEventMirror` stores provider-observed upcoming events, timing, attendee state, ETag, links, and VA ownership correlation.
- `CalendarMutation` stores create/update/cancel intent before external execution, stable idempotency, provider event ID, desired/observed state, retry state, and verification state.

## Duplicate-safe creation

Create mutations derive a stable provider event ID from the objective-step idempotency key and send that ID to Google Calendar. If an insert response is lost or a transient provider error occurs, reconciliation checks that same event ID. A later safe retry can only address the same provider object.

## Conflict policy

Routine event creation defaults to `avoid_conflicts=true`. The agent checks the primary calendar busy interval before inserting. If the requested fixed time overlaps an existing busy period and no alternate scheduling window was supplied, the objective becomes `needs_user` rather than silently double-booking.

This is a material scheduling decision, not a missing software capability.

## Verification and recovery

Create/update steps remain `verifying` until the provider event matches summary, timing, location and requested attendees. Cancellation is verified when the event is absent or provider-cancelled. Provider authentication failures become `needs_user`; transient outcomes remain reconciliation-owned by the VA.

## Attendee ownership

Attendees are sent through Google Calendar using provider updates. Mirrored attendee response state is observed during calendar sync. When all tracked invitees move out of `needsAction`, VAAPP records a durable `calendar_attendee_response_received` event, cancels pending chases and completes the waiting scheduling objective.

For events explicitly marked `expect_response`, a bounded email follow-up can be scheduled using the existing durable communications engine.

## Email-originated scheduling

Email analysis no longer directly creates a Google Calendar event. A detected `calendar_event` becomes a durable `calendar_event_planned` VA event. The autonomous core then applies the same policy, idempotency, provider execution and verification rules as manually requested scheduling work.

## API surface

- `GET /api/calendar/status`
- `GET /api/calendar/events`
- `GET /api/calendar/availability`
- `POST /api/calendar/sync`
- `POST /api/calendar/objectives`

## Android surface

Work includes a Calendar tab backed by the durable provider mirror. It shows sync health, upcoming events, VA-owned events and pending attendee responses. Manual sync remains available as an operational recovery control; normal synchronization is scheduled automatically.

## Phase boundary

Phase 3 does not claim support for non-Google calendar providers or browser-only schedulers. Those remain future capability work. Calendar mutations are real Google Calendar operations, not placeholders or simulated completions.
