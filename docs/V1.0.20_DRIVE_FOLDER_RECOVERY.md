# v1.0.20 — Drive Archive Folder Creation Recovery & Staged Upload Continuity

## Defect

v1.0.18 correctly made the exact-byte Drive file upload non-replay-safe after the
file intent is claimed. However, the provider helper still creates the archive
folder hierarchy inside `upload_drive_file()` before the actual file create.

That means the file intent can already be `submitting` when Drive is only creating
a folder. If a folder create succeeds and its response is lost, the exception is
reported to the file ledger. The file intent then becomes `creation_uncertain` even
though the file create never started. Because v1.0.18 correctly forbids replay of a
`creation_uncertain` file intent, the archive can remain permanently stranded with
no checksum file evidence that could ever resolve it.

## v1.0.20 staged boundary

v1.0.20 separates archive-folder creation from file dispatch.

Each cumulative archive path receives a `DriveArchiveFolderIntent` keyed by a
stable SHA-256 of its logical path. Folder creation has its own atomic
`prepared -> submitting` claim, one-shot provider create, and read-only recovery.

New managed folders carry:

- `va_managed_folder=true`
- `va_folder_path_key=<stable path key>`
- `va_folder_parent_path_key=<parent path key>`

Provider reconciliation prefers the exact path key. For compatibility with folders
created by older releases, a same-name folder under the exact parent can also be
bound without creating another folder. Historical duplicate candidates never cause
an additional create.

Only after the full folder hierarchy resolves to immutable Drive folder IDs does the
existing `DocumentArchiveUploadIntent` enter `submitting`. The file create is then
sent directly to that verified parent folder.

This restores the semantic meaning of the file ledger: `creation_uncertain` once
again means the actual file create may have happened.

## Response-loss behavior

If Drive accepts a folder create but its response is lost:

1. the folder intent becomes `creation_uncertain`;
2. a read-only folder query attempts to recover the immutable folder ID;
3. if evidence is not visible yet, the folder stays reconciliation-only;
4. later retries query again and never repeat that folder create;
5. the file intent remains `prepared` and has zero file-dispatch attempts until the
   folder hierarchy is fully verified.

A worker crash after a folder claim also remains fail-closed: `submitting` folder
state can only be reconciled, never replayed.

## Historical file intents

v1.0.20 deliberately does not reopen pre-v1.0.20 file intents already in
`submitting` or `creation_uncertain`. Older rows do not contain enough phase evidence
to prove whether the actual file create started. Replaying them would violate the
v1.0.18 exact-byte duplicate-suppression invariant.

## Human boundary

Drive folder/file response loss is provider/system work. It remains VA-owned and
creates no Needs You item. Google OAuth remains the existing genuine authorization
boundary.
