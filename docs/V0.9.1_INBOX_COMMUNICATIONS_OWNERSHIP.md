# v0.9.1 Inbox & Communications Ownership — Phase 2

## Objective

Phase 2 makes inbox and device communications part of the durable VA objective system introduced in Phase 1. The VA owns a conversation until the intended outcome is verified or a genuine human-only blocker is reached. It does not equate an attempted API/device call with a completed communication.

This release is cumulative: it includes Phase 1 Autonomous Core because Phase 1 has not yet been uploaded to the repository baseline.

## Gmail event ownership

`GmailMailboxState` stores the per-account Gmail history cursor, push-watch topic and expiration, latest push timestamp, history/full-sync timestamps, watch-renewal timestamp, and last error.

When Google Pub/Sub posts a mailbox notification, the HTTP endpoint validates the configured verification token, decodes the Gmail account/history notification, and persists a `gmail.history.sync` `WorkflowJob` before acknowledging the callback. The worker then requests only message additions after the stored history cursor and processes newly added INBOX messages.

A stale Gmail history cursor is not guessed around. The sync service falls back to a complete recovery sync and refreshes the cursor from the current Gmail profile. Periodic full synchronization remains enabled as recovery if push notifications are delayed or dropped.

The Gmail watch is renewed by a durable scheduled workflow when a Pub/Sub topic is configured. Runtime status is exposed through `/api/google/mailbox-status`.

## Outbound Gmail safety

Safe automatic replies no longer call the Gmail send endpoint directly from message classification. A planned reply becomes a Phase-1 VA objective and an ordered `gmail_send_reply` step.

Before a Gmail POST:

1. A `GmailOutboundMessage` intent is persisted with a stable idempotency key.
2. A deterministic RFC `Message-ID` is derived from that idempotency key.
3. The database transaction is committed before the external send call.
4. The worker checks the Sent mailbox for that RFC Message-ID before sending.
5. If the provider call times out, resets, is rate-limited, or returns an ambiguous server error, the intent is marked `creation_uncertain`; that external intent is never automatically POSTed a second time.
6. Reconciliation searches the actual Gmail Sent mailbox for the deterministic RFC Message-ID and validates the SENT label and message header.
7. If ambiguity remains unresolved for 30 minutes, the objective fails closed as `blocked_system`; it is not resent automatically.
8. Only verified Gmail evidence completes the step.

Replies preserve Gmail `threadId` and standard `In-Reply-To` / `References` headers so the response stays in the real conversation thread.

## Conversation ownership and follow-up

`VACommunicationThread` maps a Gmail/device thread to a durable VA objective and tracks whether the VA or the counterparty is expected to act next.

When the VA has sent a verified message and expects a response, it creates a `VAFollowUp` instead of relying on memory. A later inbound response records `counterparty_response` evidence, satisfies the wait postcondition, and cancels the pending follow-up. A due follow-up extends the same objective rather than creating unrelated fake work.

If a later domain-specific executor is missing, the conversation remains `blocked_capability` and VA-owned. It does not appear in Needs You solely because software capability has not yet been implemented.

## Android SMS execution

SMS is a real background-initiatable Android communication channel in this phase.

`VaSms` uses Android `SmsManager` with per-part SENT and DELIVERED `PendingIntent`s. `SmsStatusReceiver` records carrier callbacks locally and reports evidence to the backend:

- successful carrier handoff -> `sms_sent`
- successful delivery callback -> `sms_delivered`
- definitive send failure -> failed action
- later delivery failure after a proven send -> delivery failure evidence without converting the already-sent message into a retryable unsent action

If the phone temporarily cannot reach the backend after the carrier accepted the SMS, the local evidence is kept and reposted before a future worker can consider another send. This is the duplicate-prevention boundary for network ambiguity on the Android side.

## Notification-app replies

For notification-based apps, VAAPP uses the real Android notification action and `RemoteInput` while that live action is available. After Android accepts `actionIntent.send`, the app records `remote_input_dispatched` evidence.

Phase 2 does not claim recipient delivery for this evidence and does not pretend it can arbitrarily initiate a new WhatsApp, Signal, Telegram, or Messenger conversation after the notification action has disappeared. A future provider/browser executor can expand those capabilities where a real supported execution channel exists.

## Communication reconciliation worker

Android schedules a WorkManager reconciliation worker. It first reposts locally stored notification/SMS evidence, then fetches pending backend actions. Only SMS is eligible for background dispatch by this worker. This ordering prevents a temporary backend outage from turning a previously sent SMS into a duplicate resend.

## API surface

Phase 2 adds/uses:

- `GET /api/google/mailbox-status`
- `POST /api/google/pubsub`
- `GET /api/communications/actions/pending`
- `GET /api/communications/threads`
- communication action result evidence fields/statuses

The Communications Android page shows Gmail watch/cursor health and the owned-conversation ledger.

## Failure semantics

- transient provider/network failure -> wait/reconcile/recover automatically
- ambiguous Gmail send -> `creation_uncertain`, search Sent before any later send attempt
- unknown SMS outcome with no evidence -> fail closed rather than risk duplicate send
- provider authentication/configuration genuinely requiring the user -> Needs You
- missing future software executor -> `blocked_capability`, still VA-owned
- verified provider/device evidence -> step completion

## Validation gate

Phase 2 is not considered complete until the cumulative v0.9.1 commit passes GitHub Actions with the full backend dependency set and Android/Flutter build.

The automated suite includes source-contract checks plus dependency-backed behavior tests for durable email reply objectives, response/follow-up completion, Gmail follow-up persistence, and communication-delivery evidence transitions.
