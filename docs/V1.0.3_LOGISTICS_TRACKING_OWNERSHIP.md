# Full-Time VA v1.0.3 — Logistics Tracking Ownership

## Purpose

v1.0.3 fixes the semantic gap between **checking a carrier page** and **completing a logistics objective**. A successful Secure Browser run now proves only that provider-page verification succeeded and the configured page/postcondition was observed. The fulfillment layer separately decides whether that observation is terminal.

## Durable tracking observations

`FulfillmentObservation` is an additive ledger keyed to the fulfillment request/action. It records the normalized state, provider, terminal/stalled flags, source browser operation, encrypted details and observation timestamp. Existing fulfillment tables are unchanged.

Normalized states are `pre_transit`, `in_transit`, `out_for_delivery`, `available_for_pickup`, `delivered`, `exception`, `returned`, and `unknown`.

For an ordinary logistics objective, only provider-backed `delivered` completes the objective. `available_for_pickup` becomes `needs_user` because physical collection requires a person or other real-world executor, while the VA keeps a future recheck scheduled. Other non-terminal states remain VA-owned as `waiting_provider`.

## Browser observation semantics

Secure Browser verification accepts two observation-only fields in addition to its existing required provider-page postcondition:

- `settle_ms`: bounded time for a JavaScript-heavy carrier page to settle before verification/observation.
- `observe_text_any`: a mapping of normalized state names to alternative phrases. Matches are recorded as booleans/counts/hashes; raw matched text is not written to plaintext evidence.

`observe_text_any` does **not** make the browser operation pass. The recipe must still contain a real URL/title/text/selector postcondition. Conversely, a verified browser page with `in_transit` or `unknown` observation does **not** complete fulfillment.

## Rechecks and failures

Provider recipes can set `tracking.recheck_minutes`, `out_for_delivery_recheck_minutes`, `pickup_recheck_minutes`, `unknown_recheck_minutes`, `error_recheck_minutes`, and `stalled_after_hours`. Defaults are conservative and bounded.

A read-only tracking failure closes that observation action as failed but keeps the request `waiting_provider`, with bounded exponential retry. `creation_uncertain` remains `blocked_system` because VAAPP never blindly retries an ambiguous side effect.

## bpost starter template

The built-in `bpost_track_trace` starter expects a source-backed `tracking_url` and an allowlisted Secure Browser portal for `https://track.bpost.cloud/btr/web/`. The starter never invents a barcode or postcode. If the source email/order does not contain a usable tracking URL, execution remains blocked until real provider data is available.

bpost states are deliberately treated as observations, not one-shot success. bpost states that a parcel becomes trackable after bpost receives it, and that delivery/pickup status is updated through Track & Trace/My bpost. bpost also advises escalation when tracking has not changed for several working days. The VAAPP starter therefore uses repeated observation with a configurable stall threshold rather than declaring failure from a single unchanged page.

Official references used for the starter semantics:

- https://www.bpost.be/en/faq/can-i-follow-my-parcel-online
- https://www.bpost.be/en/faq/when-can-i-follow-my-parcel-track-trace

- https://www.bpost.be/en/faq/i-am-not-receiving-new-updates-track-trace-normal

## Android UX

Fulfillment now fetches provider starter templates, lets the user apply one and then edit every field, and auto-selects a matching already-configured browser portal where possible. Logistics cards show the current normalized carrier state, last observation, next automatic check and stall flag.

## Completion rule

Navigation, a successful browser action, or an `in_transit` status is not completion evidence. Completion requires the fulfillment ledger to contain a provider-backed terminal observation matching the requested outcome.
